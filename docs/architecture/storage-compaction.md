# 存储压缩说明

本轮处理表结构和实际存储放大。服务端业务表由 22 张降至 18 张，另外保留迁移表。原有 SQLite 库还可能包含桌面端自己的 `electron_state`，它不随服务端清理删除。

## 无损正文存储

`conversation_record.record_gzip` 保存可选 Gzip 二进制正文，SQLite 使用 BLOB，PostgreSQL 使用 BYTEA。大日志的 `record_json` 保留日志头和统一计算的 Token 用量；上下文与请求清单保留轻量元数据。完整读取同时选择正文列并解压，日志分页、对话恢复和请求详情不会拿元数据代替原文。

压缩从 16 KiB 开始；只有正文与元数据合计节省至少约 15% 才使用压缩。单条压缩与展开上限为 64 MiB，超过上限的原始记录保持普通 JSON。小记录不增加压缩负担，解压失败会报错，不会静默返回残缺正文。写入时同步生成编码，保持原有队列顺序；请求清单与上下文记录的去重缓存避免重复压缩已提交内容。缓存仅确认该次事务捕获的记录 ID，避免写入期间发生的后续变化被误认为已经保存；失败事务不推进缓存。

旧数据迁移按复合主键分页，只在内存中处理一条正文，不把历史日志全部载入进程。新旧数据都使用同一编码器。索引及运营统计读取元数据，不必解压整个诊断负载。

## 减少重复保存

- 运行恢复继续使用当前 durable state 和上下文头；只写不读的事件副本及历史压缩快照停止保存，已有副本在迁移时删除。工具调用去重保留。
- 记忆建议以内容指纹替代完整旧记忆快照，依然检查审核期间是否被修改。已审核建议只保留状态；终结任务清除输入，保留结果与错误；回执保留永久去重标记。
- 记忆候选、任务、回执合并为 `memory_operation`，租约、有限重试、用户隔离和会话删除语义保留。
- 一次性票据和幂等记录合并为 `request_record`。票据成功消费即删除，幂等响应在有效期内继续重放；Cookie 重绑只撤销该用户的票据，不删除其幂等记录。
- 知识版本合并到 `runtime_meta`，通过数据库触发器递增，仍能感知其他进程的提交。
- 清理六张已弃用的历史表；保留仍由桌面端读写的 `electron_state`。

## 实测与验证范围

2026-11-10 只读检查的本地库约 2.30 GiB，对话日志占约 1.22 GiB，旧运行事件占约 237 MiB。最近 8 条不小于 16 KiB 的日志样本合计 898,955 字节，编码后为 294,514 字节，减少约 67%；完整原文逐字节还原，Token 投影一致。样本编码平均约 2.41 ms，最大约 10.02 ms。这不是对整个库压缩率或其他机器性能的保证，抽样没有写回业务数据库。

独立构造的旧库覆盖事件副本、候选分页、终结与排队任务、票据、幂等记录及大型诊断数据。迁移并整理后的体积约减少 95%，此比例仅代表该构造数据。SQLite 外键检查通过，旧状态、调用去重、活动任务输入、结果和桌面状态保留。PGlite 执行了空库 SQL 和旧结构升级，覆盖触发器和二进制压缩正文。

运行函数核对覆盖审批冲突、拒绝与去重、任务领取/重试、用户隔离、票据并发消费、幂等冲突与重放、完整日志分页和上下文恢复。记忆任务以关闭模型提炼的配置验证状态机与清理，未请求真实模型。没有新增测试文件，没有运行项目 dev/build。

## 升级和磁盘回收

停止旧应用并备份数据库后再启动新代码，应用会在执行进程启动前完成迁移。大型 SQLite 升级需要临时写入空间；旧版本进程不能在迁移期间继续写旧表。后端启动等待改为可配置的 `ORBIT_API_STARTUP_TIMEOUT_MS`，默认 600000 毫秒，允许 10 秒到 1 小时，避免迁移仍在进行时被原来的 60 秒等待中断。本轮未迁移或整理正在使用的业务库。

压缩记录和删除历史数据先释放数据库内部页面。既有维护在满足 `SQLITE_AUTO_COMPACT_ENABLED`、空闲页数量及空闲比例阈值时执行 VACUUM，才将这些空闲页归还磁盘；关闭自动整理时应在维护窗口手动整理。PostgreSQL 的物理文件回收遵循其自身 VACUUM 策略，不能用 SQLite 文件大小规则推断。

当前 Docker Hub 镜像未重建；部署此功能需从更新后的源码构建。
