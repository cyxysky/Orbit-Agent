# 数据表与存储精简

当前服务端为 **18 张业务表 + 1 张 TypeORM 迁移表**，由原来的 33 张业务表先合并为 22 张，再降为 18 张。Electron 独立维护的 `electron_state` 不属于服务端初始化结构，旧桌面数据库中的此表会保留。

| 原来的存储 | 现在的存储 | 保留的约束与行为 |
| --- | --- | --- |
| 消息、步骤、日志、上下文、请求清单、文件投影（6 表） | `conversation_record` | 会话与类型复合主键、分页、轻量文件投影、消息删除级联 |
| 运行状态、事件、调用去重、压缩快照、浏览器变量（5 表） | `execution_record` | 当前状态 revision 校验、调用唯一性、变量 TTL；停止保存无人读取的完整事件与重复压缩快照 |
| 应用配置、知识版本 | `runtime_meta` | 配置独立加锁；知识版本由数据库触发器原子递增 |
| 用户引导进度 | `application_user.onboarding_json` | 独立更新，不覆盖 Cookie 绑定 |
| 记忆建议、后台任务、处理回执（3 表） | `memory_operation` | 用户与类型复合主键、会话级联、任务租约、重试与回执去重 |
| WebSocket 票据、API 幂等记录（2 表） | `request_record` | 类型与作用域隔离、票据哈希唯一、原子一次性消费、请求指纹及响应重放 |

记忆建议仅保存旧内容的 SHA-256 指纹和拟写入内容；审核期间的内容变化仍会阻止提交，读取计数变化不会造成冲突。已审核建议和已终结任务释放不再使用的输入快照，回执只保留去重信息。票据成功消费时直接原子删除，不积累已用票据。

大日志、不可变上下文和请求清单采用 Gzip 无损存储。完整正文在 `record_gzip` 中，`record_json` 保留可查询元数据；完整读取会还原原文，AI 运营仅读取小元数据。小记录、压缩收益不足的记录以及超过压缩内存上限的记录保持普通 JSON，避免增加体积或无界展开。详见[存储压缩说明](storage-compaction.md)。

升级还会删除已无生产读写的 `workflow_event`、`workflow_plan`、`task_context_state`、`task_context`、`browser_chat_defect` 和旧 `schema_migration` 表，不删除 Electron 的活动状态表或未知第三方表。

任务定义、计划、执行记录，站点账号、Cookie，通信会话和入站消息保留各自实体与约束。没有为减少数量而把不同业务强行放进一个无约束的大表。

迁移只向新结构转换，运行代码不再访问被替代的表。升级前先停止旧应用并备份数据库；需要回退时恢复备份。删除记录产生的 SQLite 空闲页需要由既有整理维护回收，表数量减少不等于文件立即同比缩小。

[PostgreSQL 初始化说明](../deployment/postgresql-initialization.md)提供空库 SQL。当前验证使用独立 SQLite 与 PGlite；真实业务库仅做只读审查。
