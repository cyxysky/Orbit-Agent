# 对话上下文管理

上下文管理负责构造来源明确、能够从中止和重试中恢复的模型请求，并按模型窗口触发历史压缩。它不维护另一份任务待办，也不根据历史目标自行安排下一步。

## 数据与职责

- `records`：不可变的内容寻址原文。用户消息、模型消息、工具调用和结果独立存储，可按引用回读。
- `history`：按发生顺序排列的对话记录引用。相同内容可以出现多次，两次相同提问是两次消息。
- `active`：当前保留的原始对话片段。不保存请求背景、运行清单或循环生成的待办。
- `continuationSummary`：唯一的历史摘要，格式为 `{version: 1, text: string}`，没有 `goal`、`nextStep` 或“继续执行”命令。
- `backgroundRef`：最近请求背景的引用，用于恢复与请求一致的 token 估算。
- `lastRequest`：精简的内部预算快照，包含数量、预算、模型以及系统提示、工具定义的引用，没有逐条保留/归档清单，不显示在 AI 输入日志中。

子任务保留独立的 history、active、摘要和检索状态，共用持久化基础设施。检查点只传递新增记录，避免每次传递整个原文集合。

## 请求构造

1. 加载所选模型窗口、单次输出上限、系统规则和实际可用的工具定义。
2. 按当前任务检索记忆和 Skill。显式选择及本轮已读取的规则优先；可选背景受独立预算限制，资料正文按需读取。历史 Skill 读取不自动成为新一轮的加载状态。
3. 构造至多一个位于对话之前的背景消息，包含历史摘要、必要知识、运行信息、时间和临时视觉证据。用户消息之后不追加任务状态或材料目录。
4. 保留对话顺序，工具调用与结果保持成对。当前用户消息按本次出现的位置保护，不做内容相似度去重。
5. 特别大的工具结果转为有限预览和原文引用。用户输入、工具调用参数和供应商推理签名不在实际请求中被局部改写。
6. 使用同一估算器计算系统提示、消息、工具 schema 和图片，再判断是否触发压缩。

`contextRead.limit` 以字符为单位，默认 8000，有效上限 16000。参数 schema 接受更大的正整数，执行时按 16000 截断，并返回 requestedLimit、appliedLimit、notice 和续读位置；不因超过有效上限阻断工具调用。搜索模式的 limit 限制摘录字符总量，目录模式每页最多 40 条，offset 的含义在参数说明中明确区分。

文件能力的必读 Skill 仅包含简短操作规则和参考目录。完整手册按章节分页注册为可选 Skill，通过目录中的 ID 按需读取，不把参考正文或整份参考目录重复加入全局 Skill 摘要。这样必读规则能完整保留在工具证据中，避免大结果被截为预览后再次触发读取门槛。

浏览器能力同样保留必读操作规则，将完整 API、弹窗交互、文本编辑、图像坐标和凭据说明作为按需参考。是否已加载必读 Skill 仍根据请求中的完整当前版本判断。

工具前置检查直接返回完整当前 Skill 时，该结果已经满足下一步的读取要求。模型应应用返回的规则并重试原工具操作，不再额外调用 skill 或 contextRead；前置检查本身不会执行原操作，也不会重复回显大型输入参数。

## 预算与压缩

窗口来自所选模型配置。单次输出上限只用于模型请求的输出参数，不从窗口中扣除，不另设本地输入预算。触发阈值与目标按模型窗口计算，目标必须低于触发阈值。token 是估算值，不冒充供应商精确 tokenizer 的计数。

先移除可选检索背景，再压缩较早的完整交互。保留当前用户消息及最近的完整交互。目标是留出后续执行空间，不为达到比例而删除当前请求。

摘要模型接收旧对话、上一份历史摘要，以及用于判断相关性的当前请求。特别大的工具输入或结果在摘要输入中提供预览及原文引用；实际原文仍在 records 中。摘要必须通过 JSON 格式、长度、引用范围和 token 减少的校验。

每批验证成功后，摘要与剩余 active 一起保存。后续批次失败或用户中止不撤销已保存的有效批次。未通过校验的批次保留原文，不使用旧任务摘要兜底，不伪报摘要完成。当前请求或完整交互无法继续压缩时保留原文，不因本地输入估算拒绝请求；实际上下文限制由模型服务商校验。摘要批次仍按窗口控制大小并校验格式与引用。

## 中止、重试与恢复

中止是会话状态，不伪造 assistant 回复供下一轮模仿。已收到的文字、调用和结果按真实顺序写入历史。依据已检查点的消息数量追加增量，不按文本猜测重叠。

网络重试复用已准备的输入和已提交摘要，避免重跑已完成的工具。摘要错误保留底层 cause，按同一请求重试策略处理，默认最多尝试 3 次；不能仅因错误类型是 ContextSummaryError 就归为不可重试配置错误。用户取消仍立即停止。只有供应商明确报告上下文超限，才降低压缩触发阈值并重新进入同一个组装器。普通参数错误不触发另一套压缩算法。

摘要请求有独立的输出预算、较低推理强度和最长 60 秒的单次等待。取消信号终止等待；格式校验失败最多要求模型重写一次，失败后清楚报错。

## 日志与统计

AI 请求详情显示适配器报告的实际请求体，包括实际消息和工具定义；适配器未提供请求体时显示模型输入。请求体不混入 contextManifest、modelContextSegmentation、执行编号或检索诊断，不裁剪消息后冒充完整输入。普通请求、原生模式和摘要请求使用同一原则。

首次响应前的等待是独立进度事件。压缩开始、批次进度和完成也有明确事件，完成只在检查点保存成功后发布。

运行中使用本轮准备的请求统计。空闲、中止或新一轮尚未组装完成时，统计当前 active、保存的请求背景、系统提示和工具定义，不用上一轮旧计数替代当前上下文。

工具问号浮层的调用前后均使用完成背景组装、大结果截断及压缩后的请求快照。调用后带有下一请求的 requestId，与下一批工具的调用前共享同一快照；同批工具显示的请求间增量不能相加。旧记录若调用前有 requestId、调用后却没有，读取时用同一轮相邻的实际请求日志恢复调用后快照；必须核对原请求时间和计数，不能跨轮或在日志缺失时猜测。缺少证据时不显示错误增量。压缩事件自身的前后统计不受此兼容处理影响。

上下文条接收请求/派发、压缩开始、已保存批次进度及成功压缩完成的统计。压缩各阶段使用组装器当时的实际消息，连同系统提示、工具定义和图片一起估算；压缩工具的前后统计也使用同一口径。准备过程中的 rawContextStats 仅供诊断，不能覆盖进度条。运行中的页面恢复直接沿用服务保存的请求统计，不重新统计暂存的原始工具大结果。

前端运行中计时使用 activity.operationId/startedAt：每次 AI 请求、工具调用、压缩分别计时，只有切换到新操作才更换起点。同一操作的心跳、内部阶段变化、刷新和组件重挂载不清零。结束后的处理记录仍可展示整轮总耗时；工具详情分别展示该工具及发起它的 AI 请求耗时。实时更新不得用较小或缺失的耗时覆盖已记录的工具耗时。工具详情从持久化记录加载完整输入，后续实时预览不得覆盖已加载的完整参数。

每次模型请求准备时将新获取的运行时时间放在系统提示开头，包括当地日期、时区和 ISO 时间；它是今天、今年和近期研究的时间基准，不能使用训练截止时间替代。背景消息不再重复注入该时间。

## 代码入口

- `runtime-context-assembler.ts`：背景选取、工具结果引用、预算、压缩计划与检查点。
- `runtime-semantic-summary.ts`：摘要输入及输出校验。
- `runtime-context-compression.ts`：工具调用链配对操作。
- `browser-chat-model-context.ts`：原始对话与持久化视图。
- `runtime-context-search.ts`：按关键词或引用回读原文。
- `browser-chat-executor.agent.ts`：模型执行边界、请求日志、重试与持久化回调。
