# 用户数据与公共知识库

## 数据边界

| 内容 | 普通业务入口的边界 |
| --- | --- |
| 对话、消息、日志、执行上下文、确认操作 | 从可信请求身份取得 userId，读取时检查会话归属 |
| 上传、生成文件、预览与下载 | 校验用户目录或所属会话/自动化运行；不以“知道文件地址”替代归属校验 |
| 文本编辑工作区 | 独立的 text-documents/<userId> 存储 |
| 自动化任务、运行记录与计划 | 普通接口将请求 userId 传入存储查询及更新条件 |
| 浏览器会话与站点 Cookie | 用户对应的浏览器配置键；Cookie 凭据按 userId 和域名保存 |
| 记忆、Skill | 私有内容归属用户；显式标记 shared 的内容允许共享读取 |
| 知识库 | 当前部署的全员公共参考库，不再按 userId 分目录 |
| AI 运营、模型和工具配置 | 管理与部署级能力，不是普通用户私有内容 |

这些是应用层归属检查，不是每用户一个数据库或容器。管理员和显式授权的宿主执行工具具有不同于普通业务 API 的权限。

## 公共知识库

- 原包、正文与索引位于 APP_DATA_DIR/knowledge/shared，不放入 public 或文件下载目录。
- Compose 将 runtime/knowledge 挂载到应用的知识目录，重建容器不丢失公共知识。
- 设置中的导入、启停和删除继续受设置访问权限保护。
- GET /api/knowledge 允许应用用户查看已启用知识包的分页目录；此入口不提供写入方法。
- 所有用户的对话、自动化与子 Agent 使用同一参考库。宿主以 readOnly: true 挂载知识能力，工具 schema、执行检查和权限声明都限制为读取。
- 记忆和 Skill 的 shared 标记不会因知识库公开而自动改变。

本机已有知识已通过 SDK 一次性复制到公共库：1 个知识包、745 条记录；原用户目录未删除。运行代码只使用新的公共目录，没有自动兼容或合并旧目录的分支。其他部署升级时，应将需要公开的原包导入公共库。

## 代码沙箱隔离修复

旧 Runner 为所有任务使用同一个 UID 10001，并给工作目录开放访问。使用合成输入并发调用 SDK HTTP 执行器，确认另一任务可以读取其临时输入文件。

现在 Linux 隔离模式使用以下通用 SDK 机制：

1. 并发任务独占不同的非特权 UID/GID，工作目录为 0700，HOME 与 TMP 均位于该目录。
2. 身份租约使用跨进程 flock 锁；协调进程退出或异常后，租约恢复会先清理该身份的进程与旧目录，才允许复用。
3. 任务及包安装进程继承 Landlock 文件策略，只允许写自身工作区，以及读取必要的系统运行库。其他任务、宿主应用目录、全局临时目录与其他进程的 /proc 内容不在授权范围内。
4. 收集输出前清理该身份的后台进程，包括脱离原进程组的子进程。输出收集完成后删除工作目录，再释放身份。
5. Linux 模式要求 root 协调进程、预置执行用户、no-new-privileges、必要协调权限以及 Landlock ABI >= 3；条件不足时拒绝执行。健康检查返回真实的运行时和隔离状态。
6. Orbit 在发出执行请求前要求 Runner 声明 linux-landlock-v1 隔离策略；旧 Runner 不满足声明时不会发送代码。Compose 健康检查要求同样的声明。

HTTP 隔离 Runner 不在 Windows/macOS 上回退为共用宿主用户；这些平台应使用 Docker 或远程 Linux Runner。显式 local SDK 执行仍属于可信开发能力，不是这个多用户隔离边界。

协调进程的 CHOWN、DAC_OVERRIDE 用于准备和回收私有目录，不授予任务进程。任务不能提升权限。Docker 的临时挂载显式启用 exec，以支持 Python 虚拟环境与原生扩展；文件访问仍由 Landlock 和 Unix 身份限制。Compose 使用 init 回收退出进程。

实现依据：[Linux Landlock](https://docs.kernel.org/userspace-api/landlock.html)、[flock](https://www.man7.org/linux/man-pages/man1/flock.1.html)、[kill](https://www.man7.org/linux/man-pages/man2/kill.2.html)。网络与容器资源上限仍使用既有配置；这里没有声称每个任务有独立的网络或资源容器。

## 验证与部署条件

2026-11-06，Linux Docker，使用无业务挂载的临时镜像及合成数据，实际通过 SDK 验证并发任务的已知文件路径、/proc 文件描述符与参数读取均被拒绝；执行用户不同，跨任务发信号被拒绝，工作区外写入被拒绝；逃逸进程组的后台进程、超时任务和身份复用后的旧目录均已清理。独立的两个协调进程也不能同时租用同一身份；强制终止租约进程后，旧任务失败，下一任务在清理旧进程和目录后才复用身份。

知识库通过两个用户的 SDK 调用和 Node 路由分发验证：读取结果一致，普通用户无法通过公共入口修改，也无法绕过设置维护权限；停用包不进入公共目录，工具只读 schema 与执行检查都有效。本轮未启动项目 dev/build，未增加测试文件。

同时验证 JavaScript/Python 执行、固定版本 npm/pip 安装和原始失败信息保留；缺少协调权限的 Runner 返回 503，非 Linux 的 HTTP 隔离运行时拒绝执行。使用上一版正式镜像验证，SDK 会在发送代码前拒绝缺少隔离声明的旧 Runner。生产类型检查及 Node 后端模块依赖检查通过。这些检查不代表对所有接口完成了全面安全审计。

本地开发配置仍允许未挂载访问使用默认用户 1，Cookie 身份绑定校验未开启，宿主执行授权处于开启状态。因此不能将当前开发配置称为多用户强隔离部署。多人服务需要可信用户身份，完成 Cookie 绑定后再开启校验，并按部署目的关闭宿主执行授权。没有在本轮擅自开启校验，避免尚未绑定的用户被锁在外面。

本轮临时镜像用于验证 SDK 执行运行时，不替代正式发行镜像。现有服务须使用更新后的 Dockerfile 与 Compose 重建并重启，才会启用修复及公共知识库；旧镜像缺少身份池和新的隔离声明，不能通过新健康检查。
