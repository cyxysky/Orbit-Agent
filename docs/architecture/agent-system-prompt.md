# 系统提示词、工具目录与运行状态

管理员在「设置 → Agent 运行 → 系统提示词」维护提示词。配置即时用于下一轮请求，部署更新后需先重启后端。管理员身份与部署授权仍由服务端检查，提示词不能扩大权限。

## 原因与调用链

此前角色说明固定列出浏览器、办公文档、记忆、知识库等能力；运行上下文还无条件加入知识包目录、办公草稿目录和浏览器账号说明。会话关闭工具时，执行端会拒绝调用，模型目录却仍可能包含工具。这会引导模型用无关工具处理普通问答，或尝试调用实际不可用的能力。

当前路径为：

1. `browser-chat-executor.agent.ts` 根据安装状态、部署授权、全局开关及会话关闭列表挂载工具。
2. `browser-chat-app-server-runtime.ts` 用同一集合创建本次模型工具定义和提示词参数，并在调用时重新检查授权。
3. `agent-system-prompt.ts` 展开管理员模板；模板为空时使用 `src/lib/agent-prompt-template.ts` 中的 `defaultAgentSystemPrompt`。
4. 浏览器交互规则仅随浏览器工具加入。账号说明、办公草稿、知识包目录分别随实际浏览器、文件、知识库工具加入。Skill 推荐只使用当前请求，旧轮次的不相关 Skill 正文不自动带入。
5. 模型协议桥再次按当前工具目录过滤工具，避免固定会话目录残留已关闭的工具。

默认提示词要求选择足够完成请求的最简单路径：能直接回答的普通问题直接回答；缺少必要事实或需要执行动作时使用工具；不为普通回复预先检索记忆、查询配置、读 Skill 或派发子任务。没有按语种、业务名称或具体问题添加服务端分流器。

## 模板与变量

| 配置 | 行为 |
| --- | --- |
| `AI_SYSTEM_PROMPT_TEMPLATE` | 替换默认主提示词；空值使用默认模板。安全、工具权限和完成校验约束仍独立生效。 |
| `AI_SYSTEM_PROMPT_VARIABLES` | JSON 字符串对象，保存管理员自定义变量。 |
| `AI_TOOL_PROMPT_MODE` | `none` 默认仅依靠实际工具定义提供说明；`available` 额外附加本次可调用工具的名称与说明。 |

内置变量：`user.id`、`session.id`、`session.url`、`model.provider`、`model.name`、`time.iso`、`time.zone`、`tools.names`、`tools.descriptions`。使用双花括号，例如 `{{model.name}}`。时间仅在模板显式引用时加入，默认模板不带每轮变化的时间。

自定义变量示例：

```json
{
  "organization": "研发团队",
  "identity": "你服务于 {{vars.organization}}，当前用户为 {{user.id}}"
}
```

模板示例：

```text
你是 Orbit 助手。{{vars.identity}}。
优先直接回答当前问题，只有需要事实验证或执行操作时才调用工具。
模型：{{model.provider}} / {{model.name}}。
本次可用工具：{{tools.names}}。
```

变量名以英文字母开头，可包含英文字母、数字、下划线和连字符。最多 100 项；变量值最多 16000 字符，展开结果最多 128000 字符。保存时拒绝未知变量、循环引用及超过 12 层的嵌套。不执行脚本、不读取文件或任意环境变量。身份、会话等运行时值按数据原样替换，不进行第二遍模板展开。

设置页提供示例值预览、变量引用按钮及恢复默认模板。预览不会读取其他用户身份或凭据。完整默认文本以源码和页面预览为准，不另存第二份模板副本。

## 自举与配置

配置管理与隔离扩展管理合并为一个 SDK 工具 `selfBootstrap`。工具列表只显示「自举与配置」，不再注册独立 `configuration` 工具。

```json
{"domain":"configuration","request":{"action":"query","domain":"catalog"}}
```

```json
{"domain":"extensions","request":{"action":"list"}}
```

`request` 分别使用配置请求和 SDK 扩展请求的原有操作结构。管理工具要求管理员身份、`ORBIT_SELF_BOOTSTRAP_ENABLED=true` 部署授权及工具开关；关闭后从模型目录与运行 Skill 目录移除。扩展仍受项目路径、工作区及权限限制。

Skill 相关推荐不是访问控制。读取用户 Skill 始终按当前用户和 ready 状态检查；没有进入推荐候选列表的可访问 Skill 仍能按 ID 读取。运行 Skill 只为当前可用工具提供参考，不能恢复已关闭工具。

## 状态、日志与流式回复

- 请求发出时显示等待首包；收到首段文本、思考或工具参数后立即切换为接收状态。首包等待与工具运行计时分开。
- 工具启动、进度和完成事件继续发布具体工具状态；通用响应快照不覆盖正在执行的工具状态。
- 子 Agent 展示「处理中」及当前工具、等待或重试状态。公开日志使用中性运行名称，隐藏执行引擎、内部线程标识、堆栈及运行文件路径；内部诊断证据保留。用户输入和工具业务参数不被当作运行元数据改写。
- 最终回复工具的 Markdown 参数在生成时发布临时草稿，不等待完整 JSON。工具参数开始流入时即发布同一调用 ID 的工具行，草稿始终在该工具行下显示；新一轮模型请求清除旧草稿。部分 HTML 不反复创建 iframe。
- 最终回复不再额外调用模型进行二次审核，也不创建审核线程。保留响应类型/参数、完成字段、尚未结束的工具和待人工输入等程序校验。业务结论是否有足够证据由主模型在执行中核对，程序校验不等于独立模型对答案正确性的评估。
- 文本形式的工具协议不会执行，也不会直接渲染在普通回复中。Markdown 代码示例保留。连续三次无效协议返回后结束为明确错误，避免无限重试。
- 原生工具和 MCP 服务列表支持拖拽及键盘排序，按用户保存。服务内工具仍通过齿轮配置分别控制。

## 执行引擎与迁移边界

当前 Agent 循环、线程历史和压缩由本地 Codex App Server 管理；Orbit 提供权限、CAP 工具、提示词、状态投影及业务持久化。`@openai/agents` 是在应用进程内运行的另一套 SDK，提供 runner、工具和交接机制，可使用应用存储的 Session。两者的线程协议与持久化状态不同，不能直接互换。参见 [官方运行时比较](https://developers.openai.com/api/docs/guides/agents#compare-agent-runtime-options) 和 [SDK 会话策略](https://developers.openai.com/api/docs/guides/agents/running-agents)。

迁移可以复用 CAP 工具及现有业务数据库，需要适配模型供应商、会话持久化、压缩策略、流式事件、取消/审批恢复和并行子任务。本轮保留当前执行引擎，移除终答的额外模型复审，并恢复工具内的流式草稿展示。

## 验证边界

取消模型复审后，使用实际运行适配器和 SDK 回复工具，配合模拟运行事件，验证终答在一轮内接受、不创建审核线程、不发起额外复审请求，完成字段校验保留；同一调用 ID 在参数流入和工具完成时复用同一 UI 周期。React 草稿组件渲染验证了正文位于对应工具行下，不覆盖其他工具草稿。没有发送真实模型请求。现有服务随后停止响应，未重启 dev/build，完整页面的流式链路仍待服务恢复后复验。

我判断可以迁移，也比较符合 Orbit 现在的架构，但属于后端执行内核的重构。CAP 工具、业务数据库、管理员提示词配置和大部分前端可以复用。

目前第三方模型的链路是：

Orbit → Codex App Server → 本地 Responses 协议桥 → AI SDK → 模型供应商

建议改成：

Orbit → Agents SDK Runner → 模型适配器 → 现有模型供应商

工具仍统一通过 CAP SDK 执行。官方也明确，Agents SDK 负责应用内的 Agent 循环，存储、工具和审批由应用控制。官方说明

具体需要修改这些部分：

| 部分 | 当前代码与迁移内容 |
|---|---|
| 执行循环 | 替换 browser-chat-app-server-runtime.ts (src/server/ai/agents/browser-chat-app-server-runtime.ts:70) 中的线程启动、恢复、工具回传和中断逻辑，改为 Agent、Runner。保留现有执行入口，供对话、自动化和子 Agent 共用。 |
| 模型供应商 | 保留 model.ts (src/server/ai/model.ts:200) 的供应商配置，通过模型适配器接入。重点核对当前 AI SDK 7 的适配版本，以及图片、思考、工具参数流和 Token 用量是否完整传递。 |
| 会话持久化 | 将 codex-runtime-state.ts (src/server/ai/agents/codex-runtime-state.ts:10) 的线程绑定改为数据库 Session 和可恢复运行状态。沿用 workspace_record，无需为此新增多张表；继续按用户、会话、主任务及子任务隔离。 |
| 上下文压缩 | 当前主执行链依赖 App Server 压缩。迁移后要明确压缩阈值、摘要、最近消息保留、截图淘汰和归档检索策略。已有上下文预算、归档和 contextRead 可以复用，但需要接入新 Session。 |
| CAP 工具适配 | CAP 当前已有 AI SDK、MCP 适配器，建议新增通用 Agents 适配器，统一处理参数校验、权限、进度、取消和结构化结果。工具实现及按需安装机制继续复用。 |
| 流式事件与日志 | 将 Agents 的文本、思考、参数增量、工具开始和结束事件，映射为 Orbit 现有事件。保留稳定的工具调用 ID，让草稿、工具状态和子 Agent 日志始终对应，前端仅需少量调整。 |
| 审批、取消和恢复 | 将现有确认入口接到 SDK 的暂停状态；审批后恢复同一次运行。保留执行日志，明确区分“未执行”“已完成”“结果未知”，避免重启后重复执行操作。 |
| 终答与子 Agent | 保留 ResponseSession、回复块和完成字段校验，以回复被接受作为结束条件，保持已移除的模型二次审核不再加入。子 Agent 继续保留独立上下文、并发限制、状态展示和完整结果回传。 |

其中有三个需要特别处理的地方：

1. Session 保存历史，不代表直接继承 Codex 的压缩行为。 建议让数据库 Session 成为模型上下文的唯一来源，业务消息和日志作为展示、审计记录，避免重复回放上下文。官方会话策略
2. 替换主引擎后，项目仍可能依赖 Codex。 当前 codex 模型供应商、辅助模型和部分媒体模型也使用 CLI。要彻底移除，需要一并调整这些入口及认证方式，随后才能清理 CLI 依赖和相关配置。
3. 运行状态恢复需要单独落地。 SDK 提供 interruptions 和 state，但保存状态、校验归属、恢复工具配置以及防止重复执行，仍需要 Orbit 实现。官方暂停恢复说明

建议实施顺序是：先完成模型与 CAP 适配，再完成 Session、压缩和恢复，随后对接流式展示、自动化及子 Agent，最后删除旧 App Server、协议桥和专属配置。

主要收益是减少协议转换和进程管理，让上下文、工具和运行状态更容易由 Orbit 统一控制。工作量最大的部分是会话持久化、压缩及中断恢复的正确性。本轮只核查了代码和官方文档，没有修改代码
